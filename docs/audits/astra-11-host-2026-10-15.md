# Astra lane 11: macOS host release review

Reviewed 2026-10-15. Scope: firmware 3.3 host selection, fixed profile, pinned image, upload/verification boundary, native reconnect guards, CLI routing and offline test coverage. No device discovery, HID operations, updater launch, flash, or canonical Application Support access was performed. Changes from this lane are restricted to this report and `firmware/upstream-hardening/lanes/11-host`.

## Verdict

No verified host release blocker found in the reviewed draft. This is an offline host review, not camera compatibility or native hardware qualification. The user's installed/pending image remains 3.2; the new host support does not establish that 3.3 was installed.

## Verified controls

- `LensImage.swift`: `.autofocusUpstreamHardened` maps to `[3,3,0]`, a distinct resource and trusted digest. It is in `FirmwareVariant.allCases`, so existing accepted-version guards in START encoding, backup parsing, journal loading, firmware observations and applied history recognize the exact version. Unrecognized versions do not become ordinary accepted custom versions.
- The variant has `supportsLensProfileChanges == false`, application base `0x5000`, end `0xa000`, and a 20,480-byte full-image pin. `personalized` requires exact equality with the frozen original Contax Zeiss 50mm f/1.4 setting, including identity/name/revision and AV 4352. Another profile or edited aperture/name fails before `DeviceService.upload`.
- `AppModel.canApplyLens` requires profile-change support. The normal Apply path uses `variantForLensChanges`, never a default version, and requests fresh-backup firmware preservation. Selecting another lens only changes local preparation. `DeviceWorkflow.primaryLensAction` routes verified 3.3 to USB tools. The explicit hardened installer separately validates the fixed profile; legacy CLI command mappings remain unchanged.
- `ApplicationImage.template`, `installedVariant`, `setting`, and `UpdateStore.load` compare the complete 3.3 application to the trusted template. Since `profileOffset == applicationBytes == 0x5000`, none admits an exception for `0x9c00..<0xa000` diagnostic bytes.
- `VerificationEngine.verify` compares every uploaded byte, then loader code, protected metadata surroundings, the entire untouched tail and factory-file hashes. The existing test now explicitly corrupts `0x9c00` for 3.3 and requires rejection. First verification therefore requires blank logs as pinned, even if a later camera cycle legitimately writes logs.
- `NativeHID.verifyUpdate` rejects the same connection identity before native access; `VerificationEngine` independently requires a different registry ID and matching serial. `NativeTransport` arms before attempting START, rejects subsequent reads/control, and the shared safety marker survives upload completion. `UploadEngine` sends only START plus exact 64-byte pages, without post-upload reads/retry/padding.
- Campaign/workbench documentation retains uploaded-but-pending 3.2 and its physical reconnect/strict verification requirement; it does not relabel the offline 3.3 candidate as installed.
