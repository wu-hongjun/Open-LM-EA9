# Follow-up 22 — exact 3.5 compiled stack review

The proposed 3.5 image in `artifacts/private/absolute35a` has a **1,560-byte
conservative conditional software stack bound**, unchanged from 3.4, against an
**8,192-byte linker reservation**. The shared-sample servo entry does not add a
wrapper frame to the linked release. The new post-read homing deadlines and
positive long-gap predictor quotient do not increase any retained application
frame. No unresolved compiled call edge, recursive component or dynamic compiler
frame was found.

This is an exact-image static review. It is not a measured high-water result,
physical stack-safety certification, elapsed-time guarantee or camera test.
The entry and interrupt caveats in [audit 18](astra-18-stack34-2026-10-15.md) and
[audit 14](astra-14-stack-2026-10-15.md) remain. The existing ELF, map, raw image,
manifest, sources and compiler records were read without rebuilding. Root owns
integration and commits; no published executable or earlier audit was changed.

## Shared-sample entry and changed paths

At `0x7f34`, `focus_run.isra.0` calls `abs_encoder_track` and preserves that
sample in `r4`; `r5` retains the absolute target. It passes those same values to
`focus_pred_begin` and then to `servo_move_from` at `0x7f5e`. The new entry at
`0x6f90` pushes five words, then four saved high-register words, then reserves
100 bytes: **136 bytes total**, matching `.su` and the old servo body's frame.
There is no initial extra encoder read in this entry. Its first loop feedback
and cancellation checks remain in the exact source reviewed by audit 19.

The relative API still exists in source and has a 16-byte compiler frame.
Its `.text.servo_move_rel` section is discarded in the linked map, and its
symbol/body is absent from the final ELF. Therefore a relative-wrapper frame
must not be appended to the release focus path. A future image that links the
wrapper needs its own graph review. Diagnostic PARK is also absent from this
release; this audit makes no diagnostic-build stack claim.

Homing remains inlined in the 104-byte `main` frame. The final drive deadline
read is the `millis` call at `0x854e`, followed by unsigned subtraction and a
300-tick comparison; the settle read at `0x85f4` is followed by subtraction and
a 500-tick comparison. They occur after the stillness sampling logic and add
no nested local allocation. `millis` is a zero-frame leaf.

The predictor still has a 24-byte frame. At `0x7872` the linked sign-bit test of
the unsigned interval branches around division for intervals above `INT32_MAX`,
retaining a zero fresh quotient. Otherwise `0x787a` calls `__divsi3`; its
conservative eight-byte divide-zero path is still included. This review
confirms the compiled stack path, not a new temporal or optical policy.

| Structural compiled chain, including live reset frame | Bytes |
| --- | ---: |
| Shared servo → pump → query → either conversion | 552 |
| Inlined homing → pump → query → either conversion | 208 |
| Shared servo → pump → predictor → signed division | 504 |
| Inlined homing → pump → predictor → signed division | 160 |

Every adjacent edge of these paths is checked against compiled calls. The
homing predictor/division row is a conservative structural path: the predictor
can be inactive and return before division during actual homing. No
path-feasibility or timing claim is inferred from the graph. The pump's query,
predictor and polling calls execute sequentially, so their descendant frames
use a maximum, not a sum. Repeated pump passes do not accumulate stack frames.

## Whole-chain and exception envelope

The deepest foreground chain is:

```text
Reset_Handler 16 → main 104 → focus_exec 96 → focus_run.isra.0 112
→ servo_move_from 136 → pump 8 → em_poll 56 → em_pump_status 40
→ em_transmit 304 → delay_us 16 → st_fail 24 → st_flush 112
→ append 104 → st_write_page 28 = 1,156 bytes
```

| Envelope | Bytes |
| --- | ---: |
| Main and descendants | 1,140 |
| Reset and deepest foreground chain | 1,156 |
| EIC software chain | 156 |
| SERCOM1 software chain | 32 |
| SysTick / default handler local frame | 0 |
| Foreground plus reset-like default-priority IRQ envelope | 1,416 |
| Foreground plus three active IRQ chains | 1,452 |
| Foreground plus all configurable levels, HardFault and NMI | **1,560** |

The all-vector result is `1156 + 156 + 32 + 6 × 36`. Each exception charges
eight core words plus one possible alignment word. The SAMD21 ARMv6-M model
has four configurable preemption levels, plus HardFault and NMI, with no
floating-point context. The unused fourth configurable level uses the zero-frame
default handler. Same/lower-priority pending exceptions and tail chaining do
not create unbounded recursive stacking. This envelope conservatively
includes combinations that EIC's configured priority can exclude.

The 6,632-byte arithmetic difference from the reservation is conditional
headroom. The reservation is not a runtime guard. `st_lock` saves PRIMASK and
masks configurable interrupts; `st_unlock` restores it; `st_fail` disables
maskable interrupts permanently. The calculation does not subtract IRQ overlap
from the deepest failure path, making that part conservative. NMI and HardFault
remain possible.

## Entry and physical limitations retained

The existing stock reconstruction at `0x2510` supports the intended MSP load
from the application vector at `0x5000`, VTOR setup, and application reset call,
evidence `ev_af84eb17e704f414c6a70060f43666c376cc40e1828175a44552db137154b0c6`.
It remains a high-confidence static reconstruction. Physical execution,
CONTROL/PSP selection, PRIMASK and inherited vector-transition state have not
been verified. The model requires thread-mode frames to use the intended
application stack.

Only EIC priority is explicitly programmed by the application. SERCOM1/SysTick
priorities, inherited enabled/pending interrupts and transition state remain
open. The model assumes intact callback/configuration memory, valid control
flow and ARMv6-M execution. It excludes memory corruption, bootloader stack
execution and failure of exception stacking itself. No stack watermark,
guard/canary, physical ISR duration, NVM timing, motor-rest, optical-response or
camera-behavior measurement was made. Stack capacity establishes no interrupt
latency or wall-clock timeout guarantee; audit 20's timing limitations remain.
